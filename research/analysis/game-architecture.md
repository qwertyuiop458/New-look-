# Архитектура игры (Game Architecture)

Архитектурный анализ воссоздает внутреннее устройство и логику работы J2ME-игры **Zombie Infection**.

---

## 1. Схема запуска и жизненный цикл (Startup Lifecycle)
1.  **Запуск мидлета:** KVM (Java Virtual Machine на телефоне) загружает и инстанцирует класс `GloftMASS`.
2.  **Активация:** При вызове `startApp()` создается единственный статический инстанс класса `g` (если он еще не создан) и биндится на дисплей: `Display.getDisplay(this).setCurrent(g_instance)`.
3.  **Инициализация потока:** Класс `g` (наследующий `Canvas`) запускает фоновый системный поток `Thread` с целевым раннером `this` (метод `run()`).
4.  **Фоновая пауза:** При входящем звонке или переключении приложения вызывается `pauseApp()`, приостанавливающий отрисовку и звуки.
5.  **Выход:** При завершении игры (переход в стейт `99` или по запросу ОС) вызывается `destroyApp(true)`, освобождающий ресурсы и завершающий поток.

---

## 2. Инициализация (Initialization)
В конструкторе `g()` и методе `fH()` происходит:
*   Определение разрешения экрана (динамическая подстройка под размер `Canvas`, в данном случае `240x320`).
*   Выделение памяти под статические буферы экрана, физические сетки карты и пулы объектов сущностей.
*   Привязка обработчика акселерометра (класс `e`) через JSR-256 Sensor API, если флаг `d.l` (vibration/sensor support) равен `true`.
*   Загрузка базовых шрифтов, цветовых палитр (`palettesAmount.bin`) и системной графики игрового интерфейса (из файла `t0`).

---

## 3. Загрузка ресурсов и уровней (Loading & Resource Management)
Игра использует блочную структуру паков ресурсов:
*   **Спрайты:** Хранятся в бинарном файле `t0`. Класс `a` парсит его при запуске, нарезая текстурные атласы на массивы кадров `Image[][]` в соответствии со смещениями.
*   **Карты и уровни:** Бинарные файлы уровней называются от `m0` до `m13_2`. 
*   **Загрузчик уровней (метод `F()` в `g.java`):**
    *   При переключении уровня игра переходит в состояние `2` (Загрузка).
    *   Считывается бинарный файл карты (например, `m3_0`).
    *   Файл содержит: ширину/высоту карты, слои тайлов, триггеры событий, координаты спауна игрока и зомби, скриптовые диалоги.
    *   Сетка коллизий карты записывается в 3D-массив `g.g[layer][x][y]` для быстрого расчета проходимости.

## 4. Главный игровой цикл (Main Game Loop)
Реализован в методе `g.run()`:
```java
public final void run() {
    do {
        long l2;
        if ((d = (l2 = System.currentTimeMillis()) - c) > 166L || d <= 0L) {
            d = 166L; // Ограничение падения FPS
        }

            this.serviceRepaints(); // Немедленный вызов paint()
        }

        long l = System.currentTimeMillis() - c;
        do {
            Thread.yield();

}
```

## 5. Диспетчер состояний (State Machine)
Управление логикой и отрисовкой разделено на две фазы:
1.  **Обновление логики (`g.o()`):** Вызывается из `paint()` перед рендерингом. Содержит гигантский `switch(a)` (где `a` — текущее состояние игры), делегирующий обработку конкретному методу обновления (например, `g.V()` для активного геймплея).
2.  **Отрисовка кадра (`g.p()`):** Вызывается следом. Содержит аналогичный `switch(a)`, вызывающий методы отрисовки (например, `g.l(Graphics)` для геймплея).

---

## 6. Обработка ввода (Input Processing)
*   **Клавиатура:** Класс `g` переопределяет стандартные методы `Canvas`: `keyPressed(int keyCode)` и `keyReleased(int keyCode)`.
*   При нажатии клавиши её маска записывается в битовое поле `g.ez` (held keys) и `g.ey` (pressed triggers). Это позволяет отслеживать одновременное зажатие нескольких кнопок (например, бег по диагонали и стрельба).
*   **Акселерометр:** Класс `e` слушает датчик наклона. При резком изменении вектора ускорения (встряхивании) взводится флаг "shake-action", обрабатываемый менеджером сущностей `f` для освобождения от захвата зомби.

---

## 7. Обновление мира и ИИ (Update & AI)
Логика обновления игрового мира (`state 3` -> метод `V()`):
*   **Игрок и Камера:** Камера центрируется на игроке с плавным сглаживанием движения. Обновляются координаты игрока на основе нажатых клавиш (`g.ez`).
*   **Менеджер сущностей (`f`):**
    *   Проходит циклом по пулу активных актеров.
    *   Для каждого актера обновляется конечный автомат анимации (класс `c`).
    *   Выполняется ИИ зомби: поиск кратчайшего пути к игроку (на основе сетки проходимости), обход препятствий, переход в фазу атаки/укуса при достижении радиуса поражения.

---

## 8. Столкновения и физика (Collisions & Physics)
*   Игра использует 2D тайловую сетку.
*   Каждый тайл на карте имеет маску проходимости (твердый блок, вода, обрыв, лестница, интерактивный объект).
*   При попытке перемещения актера (игрока или зомби) его будущие координаты (переведенные из fixed-point `>> 14` в координаты тайла) сверяются с сеткой карты `g.g`. Если тайл непроходим, движение по этой оси блокируется (скольжение по стенам).
*   Коллизии объектов между собой (пуля-зомби, зомби-игрок) рассчитываются по методу AABB (Bounding Box) на плоскости.

---

## 9. Отрисовка (Rendering)
Осуществляется через объект `javax.microedition.lcdui.Graphics` методом двойной буферизации (Double Buffering):
*   **Слои отрисовки:**
    1.  Задний фон (тайловая карта - пол, земля).
    2.  Декорации уровня (стены, колонны, препятствия).
    3.  Игровые объекты (спрайты игрока, зомби, эффекты выстрелов, кровь).
    4.  Передний перекрывающий слой (крыши зданий, арки для создания эффекта глубины).
    5.  Пользовательский интерфейс HUD (здоровье, патроны, иконка оружия, радар).
*   Все спрайты рендерятся методом `a.a(id, frame, x, y, transform_flags)`.

---

## 10. Аудиосистема (Audio & Sound)
*   Использует JSR-135 Mobile Media API.
*   Метод `ag()` в `g.java` управляет воспроизведением звуковых файлов.
*   Звуки (музыка в формате MIDI, эффекты выстрелов и рычания в формате AMR/WAV) подгружаются в виде байтовых потоков `ByteArrayInputStream` из ресурсов.
*   Создается объект `Player`, громкость регулируется через `VolumeControl`. Поддерживается циклическое воспроизведение (`player.setLoopCount(loop)`).

---

## 11. Система сохранений (Save & Load)
*   Использует системный механизм RMS (`javax.microedition.rms.RecordStore`).
*   При сохранении игры (`state 4/13` или автосейв) данные профиля (выбранный персонаж, текущий уровень, очки, купленные апгрейды оружия) упаковываются в байтовый массив и записываются в RecordStore.
*   При запуске игры через менеджер профилей (`state 16`) эти данные вычитываются, десериализуются и инициализируют переменные в классе `g`.
