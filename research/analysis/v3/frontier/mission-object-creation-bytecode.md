# Mission Object Creation — Bytecode Audit

**Метод:** прямой анализ `g.class` (major 45, J2ME) — constant pool + байткод.

## Результат

- В bytecode метод создания объекта-миссии называется **`g.aR`** с сигнатурой **`(Lf;I[BI)V`** (nameandtype CP#2833).
- CFR-декомпилятор переименовал его в `g.a(f2, n, byArray, n2)` из-за коллизии имён (в классе g сотни методов `a`).
- **5 invokestatic-вызовов** `aR` найдены в байткоде (offsets 100050, 267158, 401764, 401904, 403586) — в **5 разных методах**.
- 5 вызовов соответствуют **5 mission streams** (m9 seg10..14): каждая миссия создаёт объект-миссию L==10.

## Цепочка (доказана)

```
mission data (m9 seg10..14)
  -> aR(f2, n, byArray, n2)   [5 вызовов, по одному на миссию]
  -> f2.L == 10 -> i = f2, cB = 200, cz = n, Q[] = 4 пары из byArray
  -> cy = (ab?3:16) * d.length * 16
  -> cZ(): cB <= 0 -> g.e() -> state 7
```

## Остаётся

- Точное смещение Q[] внутри byArray (какие байты миссии) — REQUIRES_REAL_RUNTIME (поиск 8-байтового блока по паттерну неоднозначен).
- Статус: **RESOLVED_STATIC (существование/число вызовов); PARTIALLY_RESOLVED (смещения)**.
